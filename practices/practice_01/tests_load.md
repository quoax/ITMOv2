# Нагрузочные проверки

Файл ведёт OpenCode. Для учебного сервиса используем лёгкие проверки с мок‑LLM без внешних зависимостей.

| Сценарий | Нагрузка и длительность | Допустимый предел (P95) | Ожидаемые статусы | Что измеряем | Команда/подтверждение |
|---|---|---|---|---|---|
| POST /api/reviews с коротким diff | 10 rps, 60 сек, мок LLM | ≤ 200 мс | Только 2xx, error rate = 0% | Латентность, error rate | hey: `hey -z 60s -q 10 -m POST -H 'Content-Type: application/json' -d '{"diff":"x"}' http://localhost:8000/api/reviews` |
| Валидация 422 под нагрузкой | 20 rps, 30 сек, payload без diff | ≤ 50 мс | 100% 422 | Латентность при валидации | hey: `hey -z 30s -q 20 -m POST -H 'Content-Type: application/json' -d '{}' http://localhost:8000/api/reviews` |
| Стабильность при 502 | 5 rps, 60 сек, LLM always_timeout (мок) | ≤ 300 мс и P95_502 ≤ 1.2 × P95_ok | 100% 502 | Латентность и предсказуемость отказов | hey: включить режим always_timeout в мок‑адаптере; затем `hey -z 60s -q 5 -m POST -H 'Content-Type: application/json' -d '{"diff":"x"}' http://localhost:8000/api/reviews` |

## Примечания

- Под «мок LLM» понимается тестовая конфигурация адаптера, исключающая сетевые вызовы.
- Инструмент по умолчанию — hey; допускается использовать wrk со скриптом Lua. Для репозитория не добавляем внешние зависимости или jq.
- Статусы и контракт ответа согласованы с артефактами Практики 1: analysis.md (TO BE), adr.md (422/502), product_management.md (AC), tests_integration.md и tests_e2e.md.

### Что сохранять после прогона

- Дата/время запуска и инструмент с версией (hey/wrk).
- Параметры нагрузки (RPS/конкурентность/длительность).
- Распределение статусов по классам (2xx/4xx/5xx) и error rate.
- Latency P50/P95/P99.
- Заметки: конфигурация мока LLM, машина, фоновые нагрузки.
  - Для сценария «502»: зафиксировать P95_ok из позитивного сценария и сравнить P95_502 ≤ 1.2 × P95_ok.

Примеры получения значений:

- hey: после запуска скопировать блок Summary со статус‑кодами и латентностью.
- wrk: использовать раздел Latency Distribution и Non‑2xx/3xx как индикатор ошибок.

## Подсказки

Перед нагрузочными проверками запустите сервис локально (например, uvicorn) и убедитесь, что мок‑LLM активен:

```
uvicorn app.api:app --reload
```

## Как использовали AI

- Для чего: сделать сценарии проверяемыми и согласовать ожидаемые статусы (2xx/422/502).
- Тип промпта: few-shot с хорошим/плохим примером формулировок.
- Строка в [`prompts.md`](prompts.md): P2-FS.
- Что проверил студент и какие исправления поручил агенту: добавлены команды hey и ожидания по статусам; исключены jq и внешние скрипты.
