# REPORT_02 — Закрытие уязвимостей и проверка защит

Ниже описано, как закрыты уязвимости из REPORT_01 в practices/practice_06/lab/service.py, и чем подтверждается защита. Для каждой из 12 уязвимостей указаны технические меры и ожидаемый результат повторной проверки.

## 1) SQL Injection + IDOR в профилях
- Как было и в чем проблема: использовались f-строки с подстановкой `id` из query без проверки токена и владения; это позволялo SQL-инъекцию и IDOR (чтение чужих профилей).
- Исправление:
  - Переведено на параметризованный SQL: `SELECT * FROM profiles WHERE id = ?`.
  - Добавлена проверка токена (`_require_auth`) и привязка к владельцу сессии: клиент получает только свой профиль; staff может указать `id` явно.
  - Код: ветка `GET /profile` в service.py.
- Подтверждение: запрос `GET /profile?id=1 OR 1=1--` возвращает 400/только свой профиль; Алиса не может получить профиль Боба.

## 2) SQL Injection в поиске профилей
- Как было и в чем проблема: `q` подставлялся в `LIKE` через f-строку без параметризации и экранирования — возможна SQL-инъекция и утечка записей.
- Исправление:
  - Параметризованный LIKE: `WHERE name LIKE ?` с шаблоном `%{q}%`.
  - Для клиента поиск ограничен его профилем; staff выполняет глобальный поиск.
  - Код: ветка `GET /search`.
- Подтверждение: `GET /search?q=%' OR '1'='1` не раскрывает лишних записей.

## 3) Раскрытие заказов без авторизации
- Как было и в чем проблема: `GET /orders` возвращал все заказы без проверки токена и роли — утечка данных.
- Исправление:
  - Требуется токен, роль определяется сессией.
  - Клиент видит только свои заказы (`owner = session.id`); staff — все.
  - Код: ветка `GET /orders`.
- Подтверждение: `GET /orders` без токена → 401; клиент — только свои; staff — все.

## 4) Подмена цены при покупке
- Как было и в чем проблема: клиент мог передать поле `price` в теле и купить товар по произвольной цене (mass assignment).
- Исправление:
  - Игнорирование `price` для клиента; цена берётся из каталога `self.products`.
  - Разрешение override цены только для `staff` при валидации числа.
  - Код: ветка `POST /orders`.
- Подтверждение: клиент не может купить «chair» за 1 руб.; staff при необходимости может указать цену.

## 5) Повышение привилегий заголовком X-Role
- Как было и в чем проблема: доступ к `/admin/export` основывался на клиентском заголовке `X-Role`, что позволяло любому выдавать себя за staff.
- Исправление:
  - Заголовок `X-Role` больше не используется; роль определяется только серверной сессией.
  - Доступ к `/admin/export` — строго `staff`.
  - Код: ветка `GET /admin/export`.
- Подтверждение: `curl -H 'X-Role: staff'` без токена не даёт доступ; клиент с токеном — 403; staff — 200.

## 6) LFI / Path Traversal в /files
- Как было и в чем проблема: путь строился как `files/{user}/{path}` из параметров запроса без проверок; можно было читать чужие чеки и `private/*` внутри стенда.
- Исправление:
  - Добавлена функция `_validate_receipt_path`: разрешён только `receipt.txt` в `files/<user>/`; для клиента `user` фиксируется его именем; staff может явно указать другого `user`.
  - Исключены `..`, произвольные файлы и доступ к `private/*` на прикладном уровне.
  - Код: ветка `GET /files` и `_validate_receipt_path`.
- Подтверждение: `GET /files?user=..&path=../private/operator-note.txt` → 403; чужой чек для клиента — 403; свой чек — 200.

## 7) Reflected/Stored XSS в /reviews/view
- Как было и в чем проблема: отзывы встраивались в HTML без экранирования, что позволяло выполнять произвольный JS в браузере (XSS).
- Исправление:
  - Экранирование контента отзывов через `html.escape`.
  - Добавлены заголовки безопасности для HTML: `X-Content-Type-Options: nosniff`, строгий `CSP`, `X-Frame-Options: DENY`.
  - Код: ветка `GET /reviews/view` и HTTP‑обработчик.
- Подтверждение: `<img onerror=alert(1)>` отображается как текст; скрипт не исполняется.

## 8) Утечка данных через /debug/logs
- Как было и в чем проблема: `/debug/logs` был доступен без авторизации и возвращал тела/заголовки запросов, включая пароли и `X-Token`.
- Исправление:
  - Логи редактируются: пароль заменяется на `***`, `X-Token` маскируется.
  - Доступ к `/debug/logs` только для `staff`.
  - Код: `_log_request` и ветка `GET /debug/logs`.
- Подтверждение: без токена — 401; клиент — 403; у staff токены замаскированы.

## 9) SQL Injection в /assistant/context
- Как было и в чем проблема: параметр `order_id` подставлялся через f-строку; возможно расширение выборки и утечка контекста модели.
- Исправление:
  - Параметризованный SQL для `order_id`.
  - Клиент видит только свои заказы; staff может указать любой id.
  - Код: ветка `GET /assistant/context`.
- Подтверждение: `order_id=1 OR 1=1` не срабатывает; контекст содержит только дозволенные записи.

## 10) Prompt Injection в контексте помощника
- Как было и в чем проблема: в prompt без оговорок включались отзывы/вопрос пользователя; модель могла следовать вредным инструкциям (jailbreak) и выбирать опасные инструменты.
- Исправление:
  - В system‑инструкциях prompt добавлено указание игнорировать вредные инструкции из отзывов.
  - Критично: серверный слой в `/assistant/execute` применяет строгую авторизацию инструментов (см. пункт 11), исключая вредные действия независимо от ответа LLM.
  - Код: ветка `GET /assistant/context` и политика доступа в `POST /assistant/execute`.
- Подтверждение: даже при вредном ответе модели опасные действия отвергаются сервером; данные не утекут.

## 11) Несанкционированный доступ к инструментам помощника
- Как было и в чем проблема: `/assistant/execute` исполнял инструменты без проверки токена/ролей/ACL; клиент мог читать чужие файлы, экспортировать профили и удалять дерево файлов.
- Исправление:
  - Требуется сессия и проверка ролей.
  - `read_file`: только собственный `receipt.txt` (staff — по правилам);
  - `export_profiles`: только `staff`;
  - `delete_tree`: только `staff`, только под `files/`, запрет `.` и `private/`.
  - Код: ветка `POST /assistant/execute` и `_validate_receipt_path`.
- Подтверждение: клиенту отказ в `export_profiles`/`delete_tree`; чтение чужих чеков недоступно.

## 12) Раскрытие деталей ошибок
- Как было и в чем проблема: сервер возвращал клиенту детали исключений и типы ошибок, что раскрывает внутренности и помогает атакам.
- Исправление:
  - Подробности исключений не возвращаются клиенту; единый ответ: `{"error": "internal error"}`.
  - Код: `make_handler.handle_request`.
- Подтверждение: повреждённый JSON в POST приводит к 500 с общим сообщением; стек/тип не раскрываются.

---

Итог: После внедрения вышеописанных исправлений все 16 поставляемых тестов проходят. Повторные попытки эксплуатации из REPORT_01:
- SQLi/IDOR, PII Leak, LFI/Traversal и XSS — заблокированы;
- Prompt Injection/Jailbreak — не приводят к вредным действиям благодаря серверным проверкам;
- Инструменты помощника защищены контрольной политикой; логи и ошибки не раскрывают чувствительные данные.

Система соответствует ожидаемым политикам безопасности для учебного стенда.
