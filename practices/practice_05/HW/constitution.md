Constitution: SpecKit Web Application
Этот документ фиксирует нерушимые архитектурные правила. Термины MUST/SHOULD/MUST NOT трактуются по RFC 2119. Любое отступление требует изменения этого файла через формальный процесс ревизии.
1. Технологический Стек
- Backend:
- MUST: язык Go.
- MUST: БД PostgreSQL.
- MUST: слоистая архитектура: transport (HTTP) → service (domain) → repository (DB).
- MUST: все публичные функции принимают context.Context.
- Frontend:
- MUST: современные веб‑технологии (HTML5, CSS3, ES2020+, TypeScript рекомендуется).
- MUST: работа через Fetch API; управление историей через History API при SPA.
- Инфраструктура:
- MUST: миграции БД как код; миграции обязательны для любых изменений схемы.
- SHOULD: контейнеризуемость и конфигурация через переменные окружения.
2. API: Формат и Контракт (REST)
- Общие правила:
- MUST: REST поверх HTTPS, JSON — единственный формат тела ответов/запросов.
- MUST: заголовок Content-Type: application/json; charset=utf-8 для всех JSON ответов.
- SHOULD: версионирование через префикс пути /api/v1/....
- Списочные эндпоинты:
- MUST: возвращать JSON строго с двумя ключами на верхнем уровне:
- items — массив элементов.
- total — целое неотрицательное число, общее количество после применения фильтров, не учитывая пагинацию.
- MUST NOT: любые другие верхнеуровневые поля в ответе списков.
- MUST: поддержка пагинации и сортировки через query‑параметры:
- offset (целое, default=0, min=0)
- limit (целое, default=20, min=1, max=100)
- sort (строка, asc | desc, default=asc)
- MUST: стабильная сортировка; при равенстве сорт‑ключа — дополнительная сортировка по первичному ключу (например, id asc).
- Пример:
{ "items": [{ "id": "..." }], "total": 42 }
- Коды ответов:
- 200 OK — успешные чтения/операции без создания.
- 201 Created — создание ресурса.
- 204 No Content — успешная операция без тела.
- 400 Bad Request — ошибки валидации.
- 401/403 — ошибки аутентификации/авторизации.
- 404 Not Found — ресурс не найден.
- 409 Conflict — конфликт версий/состояния.
- 500 Internal Server Error — внутренняя ошибка.
3. Модель Ошибок
- MUST: единый формат ошибок:
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human-readable описание",
    "details": { "field": "must be non-empty" }
  }
}
- SHOULD: для 400 заполнять details с привязкой к полям.
- MUST: не раскрывать внутренние детали (stack traces) клиенту.
4. Backend (Go) Правила
- HTTP/Transport:
- MUST: таймауты и ограничение размеров тела запросов.
- MUST: отмена по context.Context.
- SHOULD: ETag/Last-Modified для больших коллекций, если применимо.
- Сервисный слой:
- MUST: доменная логика без зависимостей от HTTP и SQL типов.
- MUST: валидация входов и инвариантов на уровне сервиса.
- Репозиторий/БД:
- MUST: pgx/database/sql с пулом соединений.
- MUST: транзакции для согласованных изменений.
- MUST: индексы по полям сортировки/фильтрации; EXPLAIN/ANALYZE для критичных запросов.
- SHOULD: keyset‑пагинация для больших таблиц; offset/limit разрешены при соблюдении max limit.
5. Frontend Правила и UI Инварианты
- Сетевые операции:
- MUST: интерфейс обязан блокировать инициирующие кнопки/контролы на время любого сетевого запроса.
- MUST: показывать визуальный лоадер (локальный на контроле и/или глобальный индикатор) на время запроса.
- SHOULD: поддерживать отмену запросов через AbortController.
- Обработка ошибок:
- MUST: явно показывать пользователю ошибки сети (5xx) и ошибки валидации (400) понятными сообщениями.
- SHOULD: для 400 — подсветка проблемных полей/inline‑сообщения; для 5xx — уведомление с опцией повтора.
- Списки:
- MUST: использовать серверную пагинацию и сортировку через offset, limit, sort=asc|desc.
- MUST: доверять ответу { items, total } и вычислять состояние пейджера локально (номера страниц, доступность next/prev).
- SHOULD: сохранять состояние пагинации/сортировки в URL (query‑параметры) и восстанавливать его при загрузке.
6. Безопасность
- MUST: все небезопасные методы (POST/PUT/PATCH/DELETE) требуют аутентификации и авторизации.
- MUST: TLS для всех внешних соединений.
- MUST: секреты только через переменные окружения/секрет‑хранилища; запрет логирования PII/секретов.
7. Наблюдаемость
- MUST: структурированные логи (JSON), корреляция по trace/request id.
- SHOULD: метрики RPS/latency/ошибок по эндпоинтам и длительности SQL.
8. Тестирование
- Backend:
- MUST: модульные тесты сервисного слоя.
- MUST: контрактные тесты списочных эндпоинтов (формат { items, total }, границы пагинации, сортировка).
- Frontend:
- MUST: тесты на блокировку контролов, отображение лоадеров и показ 400/500.
- SHOULD: тесты пейджера и восстановления состояния из URL.
9. Производительность и Лимиты
- MUST: отклонять limit > 100 c 400 и понятным сообщением.
- SHOULD: кэширование ответов списков только при наличии стратегии инвалидации.
10. Управление Изменениями
- MUST: изменения этого документа осуществляются PR‑ом, с описанием мотивации и влияния.
- MUST: несовместимые изменения API — только через новую версию (/api/v2).
