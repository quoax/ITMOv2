Plan: Pagination and Server-Side Sorting (Unified UI/API Contract)
Статус: согласованный контракт для реализации. Термины MUST/SHOULD/MUST NOT трактуются по RFC 2119.
1) Область и цели
- Экран списка подписчиков в веб‑приложении.
- Реализовать серверную пагинацию и серверную сортировку по одному фиксированному ключу.
- UI управляет параметрами offset, limit, sort; сервер возвращает данные строго в формате { items, total }.
2) Единый API‑контракт (REST)
- Метод/путь:
- GET /api/v1/subscribers
- Query‑параметры:
- offset: integer, default 0, min 0
- limit: integer, default 20, min 1, max 100
- sort: string, enum asc|desc, default asc (направление сортировки)
- Сортировка:
- Первичный ключ сортировки: created_at
- Tie‑breaker: id ASC (стабильная сортировка)
- Семантика: sort=asc — от старых к новым; sort=desc — от новых к старым
- Ответы:
- 200 OK, тело:
{
  "items": [
    { "id": "uuid", "email": "user@example.com", "created_at": "2026-10-29T12:34:56Z" }
  ],
  "total": 42
}
- 400 Bad Request (валидация параметров). Формат ошибок (единый):
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human-readable описание",
    "details": { "limit": "must be between 1 and 100" }
  }
}
- 500 Internal Server Error (внутренняя ошибка), формат ошибок как выше с кодом INTERNAL_ERROR
- Контент:
- Заголовок: Content-Type: application/json; charset=utf-8
- Тело списка: только два верхнеуровневых поля items (array) и total (non-negative integer). Никаких других верхнеуровневых полей (MUST NOT).
- Валидация:
- offset < 0 → 400
- limit < 1 или limit > 100 → 400
- sort ∉ {asc, desc} → 400
- Пограничные случаи:
- При offset >= total сервер возвращает items: [] и актуальный total (не ошибка). Клиент использует total для коррекции страницы.
3) Backend (Go + PostgreSQL): инварианты реализации
- Архитектура: transport (HTTP) → service (domain) → repository (DB). Все публичные функции принимают context.Context.
- БД и запросы:
- COUNT (total):
SELECT COUNT(*) FROM subscribers s /* + опциональные фильтры */;
- Page query (направление зависит от sort, tie-break по id ASC):
SELECT s.id, s.email, s.created_at
FROM subscribers s
/* + опциональные фильтры */
ORDER BY s.created_at ASC|DESC, s.id ASC
LIMIT $1 OFFSET $2;
- Индексы: CREATE INDEX IF NOT EXISTS idx_subscribers_created_at_id ON subscribers (created_at, id);
- Таймзона/формат: created_at возвращать в UTC (RFC3339)
- Ограничения:
- Применять валидацию параметров до обращения к репозиторию (возвращать 400 с details).
- Соблюдать стабильную сортировку (created_at, затем id asc).
- Возвращать только items и total на верхнем уровне.
- Надёжность/производительность:
- Устанавливать ограничение limit <= 100 (жестко).
- При больших offset допустима деградация (offset‑pagination); keyset‑pagination — будущий апгрейд без изменения контракта.
4) Frontend: UI‑контракт и поведение
- Колонки таблицы:
- Email (основное отображаемое поле)
- Дата создания (формат на клиенте из RFC3339 UTC; локализованный вывод)
- id используется как ключ рендера, не отображается
- Сводка под таблицей:
- Текст: Показано X–Y из Z
- X = offset + 1 при total > 0, иначе 0
- Y = offset + items.length
- Z = total
- Пейджер:
- Кнопки: «Первая» (|<), «Предыдущая» (<), номера страниц (усечённое окно), «Следующая» (>), «Последняя» (>|)
- Состояния disabled:
- «Первая»/«Предыдущая» — при offset == 0 или во время загрузки
- «Следующая»/«Последняя» — при offset + limit >= total или во время загрузки
- Расчёты:
- currentPage = floor(offset / limit) + 1
- pageCount = total > 0 ? ceil(total / limit) : 1
- Сортировка:
- Селектор направления: asc/desc (по серверному ключу created_at)
- Смена sort сбрасывает offset = 0
- URL‑состояние:
- SHOULD: поддерживать offset, limit, sort в query‑параметрах (чтение при загрузке, запись через pushState/replaceState при изменениях)
- При первичной загрузке невалидные значения санитизируются к допустимым, URL правится через replaceState
- Загрузка и блокировки:
- MUST: на любой сетевой запрос блокировать пейджер и селектор сортировки
- MUST: показывать визуальный лоадер (локальный и/или глобальный)
- SHOULD: отменять предыдущий запрос через AbortController при новых действиях пользователя
- Обработка ошибок:
- 400: показывать явное сообщение «Некорректные параметры запроса», при наличии details — подсветка проблемных параметров; предлагать «Применить исправления» (клиппинг limit в 1,100, offset ≥ 0, sort ∈ {asc, desc})
- 5xx/сеть: баннер/уведомление «Ошибка сервера. Попробуйте повторить», опции «Повторить» и «Отмена»
- Отмена (Abort): не считается ошибкой, UI без сообщений
- Пустые и краевые состояния:
- total == 0 и items.length == 0: пустое состояние «Список пуст», пейджер скрыт или disabled, сводка «Показано 0 из 0»
- Несогласованный offset (например, данные сократились): если items.length == 0, total > 0, offset > 0 — автоматически перейти на последнюю валидную страницу:
- pageCount = ceil(total / limit)
- offset = max((pageCount - 1) * limit, 0)
- обновить URL и повторить запрос
5) Нефункциональные требования
- Безопасность/инварианты:
- Все списочные ответы — строго { items, total }
- limit на клиенте не превышает 100 (UI предотвращает)
- Наблюдаемость:
- Логи/метрики backend по эндпоинту; UI — читаемые сообщения об ошибках
- Совместимость:
- Версионирование пути /api/v1/... (будущие несовместимые изменения — через /api/v2)
6) Принятые решения по конфликтам
1. Базовый путь API:
- Было: UI — /api/v1/subscribers, Backend draft — /api/subscribers
- Решение: использовать /api/v1/subscribers (соответствует Конституции)
2. Ключ сортировки:
- Было: UI — «фиксирован на сервере (не указан)», Backend — created_at + tie‑breaker id asc
- Решение: created_at как ключ сортировки; tie‑breaker id ASC; UI показывает Email и Дату создания
3. Поведение при offset >= total:
- Было: UI предполагает авто‑коррекцию на клиенте; Backend не трактует как ошибку
- Решение: Backend возвращает items: [], актуальный total; UI автоматически корректирует на последнюю валидную страницу
4. Валидация параметров:
- Было: UI санитизирует, Backend возвращает 400 при нарушениях
- Решение: сохранить оба поведения — UI проактивно санитизирует, Backend строго валидирует и возвращает 400 с details
